## Core method (verified SCT 2026-07-04, 118 ROs)

1. **Pull closed warranty ROs** via OpenAPI `/repair-orders:search` (tekion_client.get_token, dealer_id e.g. st/876): status IN CLOSED,INVOICED, close window = the MTD/period range, filter to ROs carrying a WARRANTY pay type.
2. **The closer = `modifiedByUserId`** on the closed RO — the last user who touched it at close time. There is NO explicit "closed by" field. Validate: modifiedTime should ≈ CLOSED_TIME (matched 116/118 on SCT July MTD; the 2 misses were System auto-closes).
3. **Resolve users** via `GET /openapi/v4.0.0/users/{id}` → `userNameDetails.completeNames[DISPLAY_NAME]` + `userRoleDetails.primaryRole.persona`. Signal is CLEAN when resolved users have persona **WARRANTY_CLERK** — state this validation in the report. Unresolvable/system ids → "System (auto-close)" bucket (normal, keep it visible).
4. **Warranty $** = per-RO fan-out to `ro-invoices`, sum invoiceAmount for the WARRANTY payType. Total RO $ = sum across all payTypes. **ALL AMOUNTS ARE CENTS — /100.**
5. Output: summary table (admin | ROs closed | warranty $ | total RO $) + RO-level CSV to `/home/itadmin/tekion-reports/data/<STORE>-Warranty-Admin-Closings-<period>.csv` (grouped by admin, sorted $ desc, open/close timestamps).

## 🚨 MANDATORY WINDOW RULE — NEVER PULL A DAY AT T+1 ALONE (set 2026-08-31)

The daily job read Fri 08/28 the next morning and got **20 ROs / $7,209.68**. The settled truth was **36 / $22,116.88** — 67% of the day's warranty dollars missing. Cause: reopened ROs keep settling warranty lines after re-close, so `paySplitTotalsV3.wpAmounts.amount` is still 0/partial at the next-morning read and the `warranty > 0` filter silently drops them. **A day is only stable at T+3.**

**Every run of this report MUST do all three:**
1. **Pull the target day.** Report it normally.
2. **Count `reopenedBy` ROs in that day's list and state the exposure inline in the email** — e.g. "9 of 20 reopened; figures may restate upward." Never present a T+1 snapshot as final when reopened ROs are a meaningful share.
3. **T+3 RESTATEMENT PASS.** Also re-pull the day **3 days back**. If warranty ROs or $ moved materially (>2 ROs or >10%), send a one-line restatement to the same recipients: `Restated: <date> is now N ROs / $X (was M / $Y).`

Drift is **bidirectional** (08/26 rose 7/$1,029 → 15/$10,257; 08/24 fell 37/$21.1K → 35/$16,766). Ruled out as causes: pagination (109 rows / 109 unique, misses scattered ranks 3–108), status filter (all in-window ROs CLOSED; INVOICED/PRE_INVOICE/READY_FOR_INVOICE all `total:0`), date window (all 36 had closedTime AND modifiedTime inside 08/28). The sole discriminator is `reopenedBy`: **16/16 missing ROs were reopened; 0/11 never-reopened warranty ROs were missed.**

Corollary that supersedes older guidance in this file: **do NOT treat an off-trend LOW day as validated just because the 7-day neighbor check looks normal.** An incomplete day looks exactly like a genuinely light day at T+1. The 7-day check only proves the field path isn't broken — it does NOT prove the day is complete. Only T+3 does.
